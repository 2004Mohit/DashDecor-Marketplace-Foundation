# PHASE 1 — CUSTOMER STOREFRONT & PUBLIC PRODUCT DISCOVERY

The existing DashDecor Marketplace foundation is already implemented.

Do NOT rebuild the project from scratch.

Do NOT replace the existing API architecture.

Do NOT start Supabase, Cashfree, authentication backend, tax engine, checkout backend, Admin panel or Seller panel yet.

This phase is specifically about making the **customer-facing storefront a strong public marketplace browsing experience**.

---

# 1. CORE PRODUCT PRINCIPLE

The homepage should primarily be a place where customers can:

> **Discover and browse interior/construction materials that are available to buy.**

A visitor should be able to enter the website without creating an account and immediately understand:

* What products are available
* What categories are available
* What brands are available
* Product prices
* Product images
* Product availability
* Seller information where appropriate
* Delivery/serviceability information where appropriate

The website should NOT force a visitor to log in just to browse products.

### Important rule

**Browsing = Public**

**Transactional/personal actions = Authentication required**

---

# 2. GUEST USER EXPERIENCE

A guest visitor should be able to:

### Public actions

* Open homepage
* Browse categories
* Browse products
* Search products
* Filter products
* Sort products
* View product details
* View product images
* View product specifications
* View variants
* View pricing
* View seller information that is intentionally public
* Check delivery/serviceability where allowed
* Browse brands
* Navigate the catalogue
* Read public content

No login should be required for these actions.

---

# 3. ACTIONS THAT REQUIRE LOGIN

The following actions should require authentication:

* Add to cart
* Buy now
* Add to wishlist
* Place an order
* Save address
* View account
* View order history
* Track personal orders
* Submit a review
* Submit an enquiry where an account is required
* Access personalized/customer-specific functionality

However:

## DO NOT simply redirect the guest to `/login`.

Instead, create a reusable authentication prompt/modal/sheet.

Example:

```text
┌──────────────────────────────────────┐
│                                      │
│       Sign in to continue            │
│                                      │
│  Create an account or sign in to     │
│  continue with this action.          │
│                                      │
│      [ Continue with Login ]         │
│                                      │
│      [ Create Account ]              │
│                                      │
│          Continue Browsing           │
│                                      │
└──────────────────────────────────────┘
```

The exact design should match the DashDecor visual system.

The user should understand:

**Why am I being asked to log in?**

---

# 4. PRESERVE USER INTENT

This is important.

If a guest clicks:

```text
Add to Cart
```

the system should:

1. Detect that authentication is required.
2. Show the login/signup prompt.
3. Preserve the intended action.
4. After successful authentication, continue the intended action where technically appropriate.

For example:

```text
Guest
 ↓
Click Add to Cart
 ↓
Login Prompt
 ↓
Login
 ↓
Return to Product
 ↓
Add Product to Cart
```

Similarly:

```text
Guest
 ↓
Click Buy Now
 ↓
Login Prompt
 ↓
Login
 ↓
Continue to checkout flow
```

Do not silently lose the user's action.

If the action cannot safely be resumed automatically, return the user to the relevant product/page with a clear next step.

# 25. IMPORTANT ARCHITECTURAL RULE

Do not implement authentication itself yet.

Create the **authentication-required UX boundary**, but keep the actual authentication provider integration for the authentication phase.

For now, the application can determine guest/authenticated state using a clean abstraction.

For example:

```text
useAuth()
```

or an equivalent existing abstraction.

Do not scatter:

```text
if (!user)
```

through dozens of components.

Centralize authentication state and protected-action handling.
