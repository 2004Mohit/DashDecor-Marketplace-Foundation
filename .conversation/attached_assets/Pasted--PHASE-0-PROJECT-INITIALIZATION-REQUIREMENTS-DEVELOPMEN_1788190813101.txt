# 6. IMPORTANT BUSINESS ARCHITECTURE

The following concepts must remain separate.

```text
Product
   ↓
Seller Listing
   ↓
Seller Inventory
   ↓
Customer Order
```

Do NOT design the system around:

```text
Product → stock
```

as a single global stock value.

Seller inventory is authoritative for seller-owned listings.

The architecture must allow the same canonical product to potentially have multiple sellers/listings.

---

# 7. PRODUCT LISTING WORKFLOW

Seller product submission must support:

### Option 1

Seller uploads:

* Product photos
* Catalogue
* Material information

### Option 2

Seller manually fills product fields.

Both methods must enter the same controlled workflow:

```text
Seller
  ↓
Submit Product
  ↓
Admin Review
  ↓
Admin Creates/Edits Listing
  ↓
Seller Review
  ↓
┌──────────────────┬────────────────────┐
│ Approve          │ Request Change     │
↓                  ↓                    │
Admin Approval     Admin Revision ←────┘
  ↓
Published
  ↓
Customer
```

The architecture MUST support:

* Revision history
* Status history
* Change requests
* Admin edits
* Seller confirmation
* Seller rejection/correction request
* Image revisions
* Auditability

Do not implement this as a simple boolean such as:

```text
approved = true
```

The final workflow must be stateful and auditable.

# 8. DYNAMIC PRODUCT ATTRIBUTES

Categories are created and managed by Admin.

Support:

* System fields
* Category-specific fields
* Optional fields
* Seller-suggested custom fields
* Admin approval of custom fields
* Reusable approved fields

Seller-created fields must NEVER automatically become marketplace-wide fields.

Example:

Seller suggests:

```text
Foam Density
```

Admin can approve it for the appropriate category.

Only then can it become reusable.

Do not hard-code category attributes into React.

# 11. TAX / GST

Tax must NOT be hard-coded into frontend code.

The system will eventually use:

```text
Product / Category
        ↓
Tax Classification
        ↓
Transaction
        ↓
Applicable Tax Rules
        ↓
Tax Calculation
        ↓
Tax Breakdown
```

Support the data model for:

* CGST
* SGST
* IGST

where applicable.

Tax rules must be configurable by Admin.

Most importantly:

**Historical orders must not change when Admin changes future tax configuration.**

Therefore, final tax calculations must eventually be persisted as transaction/order-level financial snapshots.

Do not implement tax logic in this phase yet.

# 19. SECURITY REQUIREMENTS

Security is a first-class requirement.

Never:

* Expose Supabase service-role keys to the browser
* Put payment secrets in frontend code
* Trust client-side prices
* Trust client-side tax calculations
* Trust client-side commission calculations
* Trust client-side payment-success state
* Use UI hiding as authorization
* Allow sellers to bypass Admin listing approval
* Allow customers to modify order totals
* Allow arbitrary users to access other users' private data

Use environment variables for secrets.

Create `.env.example` containing placeholder variable names only.

Do NOT create real production credentials.

Clearly document which variables are:

* Client-safe
* Server-only

Never expose server-only secrets through `VITE_*`.
